The 2026-11-02 declaring-assembly audit corrects the parser's original signature
substring heuristic. A parameter/return-type mention of Lython does not make a
method part of the core. The original B77 self totals remain 436/279 after the
[precise audit](declaring-assembly-correction.json); code bytes, offsets and raw
captures are unchanged. The parser includes controls for these false positives.

2026-11-01. Recovered native code from the **original, stopped B71 workers**;
no workload rerun, new capture, retiming or runtime change. The historical capture
is `d703767c`, core source `9003d045`; current casing correction `4cae38f4` remains.

The saved method-level profile cannot distinguish opcode dispatch from inlined
handlers, checks and value transfers. Original workers 2951179/2951198 had left
their matching jitdump files in the VM's `/tmp`. Both processes are absent.
Read-only recovery records source paths, timestamps, sizes and hashes. These are
diagnostic bytes generated by the managed CLR, not runtime source or dependencies.

Other mapped samples belong to CLR/shared-library code. Code-load names and
addresses distinguish actual Tier1/OSR versions; a freshly JITted method is not
used as a substitute. Methods with at least ten guest self samples are disassembled
offline using objdump. Every selected sample offset resolves to an instruction.
Neither dump contains source-line debug records.

For example, the loop's 150-sample OSR interpreter has samples on an integer
comparison at +0x8a (16), a conditional branch at +0xa79 (14), a reference store
at +0xab2 (10) and a load at +0x101 (9). The emitted loop includes guards, stack
and local transfers, handlers and a switch. These observations do not establish
their removable costs. CPU-clock samples can skid; pointer offsets and unresolved
indirect call targets cannot be assigned invented C# source identities.

Source review confirms current execution checks are already an inlined terminal
admission test and current-token cancellation test. It does not justify removing
them or introducing a checkpoint counter. Earlier fusion, linear-engine, explicit
input and call-arena trials remain closed. The CSV parser already processes UTF-8
segments; this evidence does not establish another UTF-16 conversion pipeline to
remove there.

**Stop this offline assessment. No runtime candidate is selected.** Exact code
improves attribution beyond method labels, but missing source maps, unresolved
calls and distributed whole-script work do not demonstrate a coherent dominant
removable mechanism. No speedup, causal fraction or new CPython ratio is claimed.

## Evidence and parser limits

[Recovery identities](recovery.json), [assessment](assessment.json), per-capture
method/offset records and [instruction observations](instruction-summary.json)
preserve the unmapped samples. [Original code](original-jit-code.tar.gz), SHA256
`3255dddb61f5c2c602808138c6e00d7cc58c53d0e15ae8a67a319280646c50fa`,
and [offline disassembly](offline-assembly.tar.gz) retain the exact bytes.
[Parser](analyze.py) uses the primary Linux
[jitdump format specification](https://raw.githubusercontent.com/torvalds/linux/master/tools/perf/Documentation/jitdump-specification.txt).

The first strict parser rejects CLR stub-region records that declare a range
without supplying bytes. They are retained as declarations, never disassembled
as if code existed. A second global overlap check encounters overlapping declared
ranges. Final attribution checks all candidates for **each sampled address** and
rejects ambiguous addresses; the actual guest samples have none. No moved-code
records occur. These offline parser corrections add no guest execution and do
not change the saved samples. Reproduction should use a private scratch copy of
the parser/archive, run from the repository root so the original B71 capture is
available; derived files are written beside the scratch parser.
